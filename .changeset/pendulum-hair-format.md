A physics rig may take several inputs, each following or lagging. `IkiPhysics` carries `input` or `inputs` (a non-empty list), exactly one of the two, each entry an `IkiPhysicsInput` `{ parameter, weight, mode? }`; every input's signed-normalized value × `weight` sums into the spring's one target. `mode` is `"follow"` (also when absent, today's behavior: the output carries the spring's position, so a held value holds it displaced) or `"lag"` (the output carries `scale·(x − target)` for that input's share, so it swings while the value moves and a held value returns it to rest). `physicsInputs(rig)` returns a rig's inputs whichever form it declares.

Both are opt-in: a rig without them parses to the same object as before. The new rules throw a path-qualified `IkiFormatError`: both forms or neither at `physics[i]`, an empty list at `physics[i].inputs`, an undeclared parameter, a non-numeric weight, a mode other than the two or a parameter repeated within the list at `physics[i].inputs[j]` (a bad mode on the single form at `physics[i].input.mode`), and an entry equal to the output as `physics[i]: inputs[j].parameter and output.parameter must differ`; no rig's output may equal any input of any rig. Earlier versions silently dropped `inputs` beside `input` and any `input.mode`, so **a rig carrying both forms, or an `input.mode` other than `"follow"` or `"lag"`, used to load and now fails to load**. `IKI_FORMAT_VERSION` is unchanged (v1 is unstable before 1.0), but **a rig with only `inputs` is rejected by an earlier `@ikijs/format`, and an earlier one drops `mode`**, so a host on an older format plays a lag input as follow.
